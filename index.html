Tinker is an ontology-driven builder for internal tools. Define an object once and it becomes a real Postgres table behind row-level security, a governed API, and an MCP front door for agents. Personal data is sealed by type. Every read gets a mask and automations get a key. A person sees the value only when a second person approves.

01 — SEALED FIELDS

One field.
Three faces.

Email and phone fields are personal data by type, so they are always sealed. Text fields opt in. The core database never holds the value. It holds a vault reference and a keyed blind index, and each audience gets exactly the face it needs.

default

Masked in the compiler, not the UI.

The typed query compiler writes the mask into the SQL itself, so every consumer that builds on it inherits the mask and none of them can forget it.

  • Exact match still works. eq, ne and in go through the HMAC-SHA256 blind index.
  • Anything that would leak is refused. That covers contains, ranges, sorting and row policies on sealed fields.
  • Copied sealed forms are rejected. You can't paste one record's vault reference into another.
// MCP · query
{ "object": "customer",
  "intent": {
    "select": ["name", "email",
               "phone", "plan"],
    "filters": [{
      "field": "email", "op": "eq",
      "value": "Ada@Analytical.Engine " }] } }

// → rows, matched via email__bidx
[{ "name":  "Ada Lovelace",
   "email": "••••••",
   "phone": "••••••",
   "plan":  "Enterprise" }]

// "order": [{ "field": "email" }]
error: field 'email' is sensitive and
       cannot be sorted on
automation key

Stable for a value. Useless to anyone else.

pk_ followed by 40 hex characters of HMAC over the blind index, in a separate domain. The same email always gives the same key, so you can join, dedupe and route on it. The key won't query the index and can't be reversed.

  • Scoped per field, like the index. Keys are never comparable across objects, which keeps cross-object linkage closed.
  • Shows up wherever a value would leak: run logs, webhook payloads, exports.
// MCP · query, selecting keys
{ "object": "customer",
  "intent": { "select": ["name", "email:key"] } }

// → rows
[{ "name": "Ada Lovelace",
   "email:key": "pk_3f9a0c71e2…b84d" },
 { "name": "A. Lovelace",
   "email:key": "pk_3f9a0c71e2…b84d" }]
// same person, found without seeing the address
four eyes

Plaintext is an event, not a read.

The reveal tool returns one field of one record. It needs an owner or admin with an explicit scope, a stated purpose, and an approval decided by someone else. That approval works only once.

  • The vault is a separate database with its own roles. Core SQL can't join to it, and a test proves that.
  • Each record has its own key (AES-256-GCM, wrapped by a rotating KEK), so erasing the record destroys the key.
// MCP · reveal
{ "object": "customer",
  "record_id": "01J9…7f2c",
  "field": "email",
  "approval_request_id": "01J9…a40e" }

// → value (audited as pii.reveal)
"ada@analytical.engine"

// same approval, second time

  approved by someone else
02 — THE DATA PATH

Every path goes
through the governor.

The builder, the HTTP API, the CLI, live grids, search, dashboards and agents all go through one compiler. Tenancy is enforced in Postgres, not in application code you have to trust.

01 · CREDENTIAL

Who is asking

Machine keys (tk_…), passkeys (WebAuthn ES256/EdDSA, UV for MFA) or OIDC code flow with PKCE, state and nonce. Each resolves to one actor, one org and one role.

02 · TENANT TX

Which org, by the database

SET LOCAL app.organization_id inside a transaction on a role that can't bypass RLS. The tenant comes from the credential, never from the caller.

03 · COMPILER

What they may see

Role projection, row policies, masking and the blind index are compiled into one SQL statement. Unauthorized rows come back not_found, so there's no existence oracle.

04 · GOVERNED WRITE

How it changes

Validation, lifecycles (draft → review → publish), approvals bound to the action, and an automation event written in the same transaction.

CORE · PG18

Real tables

One table per object. Sealed columns hold a vault ref plus __bidx.

no join
VAULT · PG18

Ciphertext

Per-subject DEKs wrapped by the KEK, with every access audited.

Ontology → real tables

Objects, fields, relations and lifecycles are metadata that materializes into real Postgres DDL, not an entity-attribute-value store. Schema changes ship as versioned evolutions with canary and promote.

Fail closed, loudly

A missing extension, an unset vault, a dead IdP or a half-configured key gives a typed error at startup or call time. Nothing silently falls back to plaintext.

Durable by default

DBOS-style workflows, queues and timers on Postgres itself. Outboxes for email and automations mean no event is lost and none is invented.

03 — AUTOMATIONS

Automate on email addresses
no one can read.

Conditions compare keys and actions resolve values only at the moment they run. Typed literals are turned into keys when the automation is saved. The saved definition never contains the plaintext you typed into it.

tx

Outbox in the same transaction

An event exists exactly when the write commits. Workers claim with SKIP LOCKED, and each (automation, event) pair runs once.

3

Loop depth

Writes made by an action carry the chain depth forward. At depth 3 the run records loop_blocked and stops.

20/h

Guessing guard

An equality literal is a yes-or-no question about a value, so each actor can save at most 20 sealed literals per hour. Saves are audited with counts only.

=

Never sees more than its author

Runs as the author's role, under that role's projection and row policy. If the author loses the role, the next run fails closed.

04 — REVEAL

Two people.
One field. One time.

This uses the same four-eyes approvals that guard publishing, bound to the exact (object, record, field). The approval is consumed atomically with the reveal.

1
SB
support-botagent · tk_ key · admin

Asks, with a reason

It files a pii.reveal request for one field. The purpose is stored and audited.

request_reveal { field: "email", purpose: "support ticket 42" }
2
MR
Maya R.human · passkey · admin

Someone else decides

A different owner or admin lists the pending requests and approves or denies them. The requester can never decide their own request.

approvals { action: "list" } approvals { action: "approve", id: "01J9…a40e" }
3
SB
support-botsame requester

Reveals, once

It must come from the same requester, for the same field, before the approval expires. The vault decrypts in-process and logs the access.

reveal { field: "email", approval_request_id: "01J9…a40e" } → "ada@analytical.engine"
✕

Self-approval. The requester is recorded on the request and refused at decision time, whether they approve or deny.

✕

Replay. A second reveal with the same approval fails. So does a reveal of a different field or record.

✕

Blanket scopes. mcp:tools doesn't cover reveal. The key needs mcp:tool:reveal by name.

05 — ERASURE

Forget someone
by destroying a key.

Every record has its own data-encryption key. Erasure tombstones the refs, nulls the columns and destroys the key, so any copy of that ciphertext, in a dump or a replica, becomes noise.

wrapped_deks · one per subject

Erase rec_…7f2c

The MCP erase tool, gated like reveal and audited as pii.erase, destroys every value for the record (row, drafts, versions, superseded copies). It then shreds the subject's DEKs. One record's erasure never touches anyone else's key.

Honest limits. A backup that also contains wrapped_deks still holds the key until it ages out, so back up the key table on a shorter retention than the values. Values sealed before per-subject keys sit under a legacy org key; erasure destroys them row by row but can't shred that shared key.
06 — AGENT FRONT DOOR

An API no model has seen,
that teaches itself.

Tinker isn't in any model's training data, so the MCP server is designed to be self-describing. An agent with nothing but a tk_ key discovers the schema, learns the governed write paths and does correct work. Agents only ever see the mask.

Objects, fields, lifecycles and allowed operations for this role.

query

Typed, governed reads with filters, keys and blind-index matches.

get_record

One record, projected and masked for the caller.

create_record

Validated, sealed at entry, with an outbox event.

update_record

Governed update; changed fields feed triggers.

Lifecycle moves: draft, review, publish.

covered by mcp:toolsneeds mcp:tool:<name> by name, and owner or adminstdio and HTTP/SSE · tinker://ontology/{slug} resources

“If the front door doesn't win clearly, it failed.”

That was the bar Tinker set itself: median time to the first correct publish for a fresh agent, measured against raw HTTP plus human docs. Across three timed, independently verified experiments, adding skill docs on top of the MCP never beat the MCP alone; every verdict was a loss or a tie. The MCP documents itself.

Machine keys that mean something

A tk_ key is bound to one organization and one role at issue time. Sessions take their tenant from the credential, never from the request. Unknown arguments are rejected with a teaching error, not ignored, so an agent learns the real shape instead of guessing.

08 — EVIDENCE

Every claim
names its test.

The status ledger ties each capability to a passing test, and the important ones were checked by breaking the code on purpose to see the test fail. Here are some that guard what this page claims.

  • ✓
    sensitive_values_are_sealed_masked_findable_and_revealable

    No plaintext in the row or the audit log, exact match through the index, and plaintext only through reveal.

  • ✓
    reveal_needs_a_fresh_second_person_approval_for_that_field

    Self-approval, replay and field substitution are all refused.

  • ✓
    erasure_crypto_shreds_copies_of_the_ciphertext

    The subject's key is gone, and a restored copy of the ciphertext is refused.

  • ✓
    sealed_conditions_route_and_actions_resolve_only_at_send

    Keyed conditions match, and the recipient is resolved only at send.

  • ✓
    runs_fail_closed_when_the_author_loses_the_role_and_stop_when_disabled

    An automation never outlives its author's authority.

  • ✓
    webauthn_register_then_login_binds_origin_and_assurance

    Phishing origins, counter replay and UV assurance are covered.

  • ✓
    oidc_token_abuse_fails_closed

    PKCE, single-use state and nonce binding. A bare id_token is refused.

  • ✓
    ingest_seals_sensitive_fields_and_scrubs_landing

    Imported PII is sealed at promotion and scrubbed from the landing tables.
